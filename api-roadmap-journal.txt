--- Étape 3 — apps/api/src/modules/auth/auth.service.ts ---
Fait, vérifié, RAS après corrections. Flow OAuth2 Discord en 4 étapes +
signature JWT :
  1. getDiscordAuthorizeUrl()    -> construit l'URL Discord (pas de call réseau)
  2. exchangeCodeForToken(code)  -> POST /oauth2/token
  3. fetchDiscordUser(token)     -> GET /users/@me
  4. fetchManagedGuildIds(token) -> GET /users/@me/guilds, filtré par :
       a) permission MANAGE_GUILD (bitfield 0x20n, test bit à bit avec &)
       b) présence réelle en base (table guild) via guildRepository +
          In(managedGuildIds)
  handleCallback(code) orchestre tout, jwtService.sign({ sub, username, guilds }).

DECISION IMPORTANTE (rappel) : bot privé, présent sur seulement 2 serveurs
Discord, remplis manuellement en base (apps/bot est vide, aucun code bot
n'existe encore) :
  1105249695644786791 -> Wystrelia (officiel)
  1508798654796795924 -> Wystrelia-dev
D'où le filtre b) ci-dessus, obligatoire en plus de la permission Discord.

--- Étape 4 — apps/api/src/modules/auth/auth.controller.ts ---
Fait, vérifié, RAS après corrections. 4 routes : GET /auth/discord,
GET /auth/discord/callback, POST /auth/logout, GET /auth/me (protégée
par JwtGuard seul, pas de GuildGuard ici puisque pas de :guildId).

Bugs trouvés et corrigés pendant la session :
  1. Import `Response` depuis 'express' manquant au départ -> TS
     résolvait vers le Response du DOM (fetch API) au lieu d'Express.
  2. `import { Response }` -> `import type { Response }` nécessaire
     (isolatedModules + emitDecoratorMetadata : un type utilisé en
     paramètre décoré doit être importé en import type s'il n'existe
     pas comme valeur runtime).
  3. `res.redirect(DASHBOARD_URL)` manquant après avoir posé le cookie
     dans handleDiscordCallback -> l'utilisateur restait bloqué sur la
     route de callback. Corrigé.
  4. `JwtGuard` utilisé dans @UseGuards(JwtGuard) sans être importé.
     Corrigé (import { JwtGuard } from './guards/jwt.guard').

Concept discuté en profondeur : @Res({ passthrough: true }) vs @Res()
seul (passthrough garde la gestion automatique de la réponse par Nest
tout en permettant res.cookie()/res.redirect() ciblés).

--- Étape 5 — apps/api/src/modules/auth/guards/jwt.guard.ts ---
Fait, vérifié, RAS après correction. Lit request.cookies['token'],
jwtService.verify() dans un try/catch -> UnauthorizedException si
absent/invalide, sinon attache le payload à request.user.

Fichier associé créé : apps/api/src/types/express.d.ts
  declare global { namespace Express { interface Request { user: {...} } } }
  export {};
Bug trouvé et corrigé : le `export {};` final manquait au départ ->
sans lui, TS traite le fichier comme un script global (pas un module),
et declare global ne fusionne pas correctement le type Request importé
ailleurs depuis 'express'. D'où l'erreur "Property 'user' does not
exist on type 'Request'" vue dans jwt.guard.ts ET auth.controller.ts en
même temps (même cause racine, un seul fichier à corriger).

Discussion : pourquoi express.d.ts ne va PAS dans packages/shared (qui
ne contient que des entités TypeORM réellement partagées entre apps) --
c'est une augmentation globale d'un type tiers (Express), qui n'a de
sens que là où express/@types/express sont utilisés, donc seulement
apps/api. Reste local à apps/api/src/types/.

--- Étape 6 — apps/api/src/modules/auth/guards/guild.guard.ts ---
Fait, vérifié, RAS après correction. Vérifie que request.params.guildId
fait partie de request.user.guilds, sinon ForbiddenException (403, pas
401 -- distinction volontaire "on sait qui tu es mais pas le droit ici").

Bug trouvé et corrigé : erreur TS "Argument of type 'string | string[]'
is not assignable to parameter of type 'string'" sur .includes(guildId).
Cause : ParamsDictionary d'Express type toute valeur de req.params comme
`string | string[]` (à cause du support des routes wildcard type
`*id` qui peuvent capturer plusieurs segments). Fix : typer explicitement
le générique de Request avec la forme réelle des params de cette route
précise : context.switchToHttp().getRequest<Request<{ guildId: string }>>()
-> guildId redevient un `string` simple, sans cast ni vérification
runtime supplémentaire.

--- Étape 7 — Appliquer les guards ---
Pas de fichier dédié -- c'est une règle à appliquer à chaque nouveau
controller Phase 4 avec :guildId dans sa route :
  @Controller('guilds/:guildId/xxx')
  @UseGuards(JwtGuard, GuildGuard)   // ORDRE IMPORTANT, voir plus bas
  export class XxxController { ... }

Concept discuté : l'ordre dans @UseGuards(...) EST l'ordre d'exécution.
JwtGuard doit toujours être avant GuildGuard, puisque GuildGuard lit
request.user.guilds, qui n'existe que si JwtGuard a déjà tourné et a
réussi (sinon il lève une exception et coupe la chaîne avant GuildGuard).
Rappel des 3 niveaux où @UseGuards/guards peuvent s'appliquer : méthode,
classe (celui utilisé ici), ou global via app.useGlobalGuards() dans
main.ts (pas utilisé dans ce projet, certaines routes comme
/auth/discord ne doivent surtout pas être protégées).

Appliqué concrètement cette session sur filtered-word.controller.ts
(voir section Phase 4 ci-dessous) -- premier vrai test de la règle.
